# VulnFounder 项目内运行时与全局设置改造计划

## 1. 目标

让 VulnFounder 在 Linux x86_64 交付目录中优先找到 OpenHarmony 动态验证所需的工具和资源，降低用户首次部署时手动寻找工具链、HDC 和 HAP 签名材料的成本；同时把 OpenGrok 地址、项目、版本和相关认证引用集中到设置页管理，避免扫描页面重复要求用户填写。本次不下载 Linux 工具包，只定义导入位置、版本清单和诊断规则。

本计划不把主机操作系统运行时（Python、Go、Java、系统动态库）伪装成“已经随项目交付”。这些组件受平台和许可影响，项目只负责检测、提示和使用；可以随项目分发的 OpenHarmony 工具、HAP 构建运行时和研究用签名材料，则采用项目内目录和清单管理。

## 2. 边界与安全原则

1. 工具解析顺序统一为：显式设置或环境变量 → 项目内运行时包 → 系统 `PATH` 或系统 SDK → 仅保留兼容性的旧路径。解析结果必须带来源，不能默默使用扫描仓库中的同名程序。
2. 项目内运行时使用相对路径和版本清单，不保存任何开发者机器的绝对路径。
3. HAP 私钥和密码不提交到 Git、不写入日志、不在前端回显。项目内工具链随附的 SDK 测试根材料只用于按当前设备 serial 生成临时 debug profile；生产证书仍由用户通过受保护文件导入。
4. OpenGrok URL 不允许携带用户名、密码或 API Key；令牌只能引用环境变量名，页面只显示“已配置/未配置”。
5. 设置变更必须原子写入项目配置文件（权限 0600），并保留未知配置字段，不能破坏已有模型配置。

## 3. 目标目录布局

```text
VulnFounder/
├─ runtime/
│  └─ openharmony/
│     └─ linux-x64-6.1/          # Linux 部署方导入的运行时包（本次不内置）
│        ├─ hdc
│        ├─ hvigor/bin/hvigorw
│        ├─ tool/node/bin/node
│        └─ sdk/default/openharmony/toolchains/
│           ├─ hdc
│           └─ lib/hap-sign-tool.jar
├─ config/
│  └─ hap_cert/                  # 本机私有目录，默认 0700/0600
│     ├─ README.md
│     ├─ manifest.json           # 只记录文件名、用途、SHA-256，不记录密码
│     ├─ oh_release_chain.cer
│     ├─ oh_profile8.p7b
│     └─ oh_release.p12
└─ config/vulnfounder/
   ├─ config.example.json
   └─ config.json                # 本机配置，默认 0600，不提交
```

正式交付目标是 Linux x86_64。当前本机 macOS arm64 运行包只用于验证，不进入 Linux 交付包。部署方需要导入匹配版本的 Linux 工具；不能把 macOS 工具直接当作 Linux/Windows 工具使用。没有完整 SDK 时，HDC 和签名工具仍可被发现；HAP 构建器会报告缺少的 Node、Hvigor 或 SDK，而不是静默回退到不兼容路径。

## 4. 实施任务

### 阶段 A：运行时基础

**任务 A1：统一运行时解析器。**

在 Python 侧提供 OpenHarmony runtime resolver，统一返回 toolchain 根目录、HDC、Hvigor、Node、签名 JAR、Java 和证书目录，并附带 `source`、版本和可执行权限信息。现有 HDC、HAP transport、Claude Code 辅助构建和自动协议工具全部改用该解析器。

验收：设置环境变量、使用项目内路径、只使用 PATH 三种情况下解析结果可预测；不存在的工具会给出具体缺失项。

**任务 A2：运行时清单和健康检查。**

增加 `runtime/openharmony/*/manifest.json` 示例及检查命令/接口，清单记录平台、OpenHarmony 版本、文件相对路径和 SHA-256。健康检查不执行未知二进制，只检查路径、权限、文件类型和摘要；HDC 连接检查单独执行。

验收：前端可看到“已找到/缺失/权限不正确/摘要不匹配”，不会显示私钥内容。

### 阶段 B：项目内资源与证书

**任务 B1：工具链导入与项目内默认路径。**

当前工作区可保留 macOS arm64 的完整 command-line-tools 作为本机验证材料。由于约
6GB 且平台相关，Linux 交付包不包含这份 macOS payload，也不在本次工作中下载
Linux 工具；部署方按清单导入匹配的 Linux 版本。后续可按平台提供“完整包”和
“最小动态包”两种清单模式，动态包至少包含 HDC、Hvigor、Node、HAP 签名 JAR 及
HAP 构建所需 SDK 部分。

验收：清洁环境只设置项目根目录即可发现项目内工具；路径迁移到另一目录后仍可用。

**任务 B2：签名材料本地受保护管理。**

提供 `config/hap_cert/README.md`，说明所需文件、用途、权限和导入方式。检查目录 0700、私钥 0600；只输出文件名和摘要。缺少正式证书时允许使用项目内 SDK 测试根材料按当前 HDC serial 生成临时 debug profile，但不得把它展示为生产证书，也不得在没有设备或工具链校验时伪造成功。

验收：缺证书、权限过宽、文件摘要不匹配时均有可读诊断；通过检查后才能进入 HAP 签名步骤。

### 阶段 C：设置页与配置持久化

**任务 C1：扩展设置模型。**

在现有配置文件中增加 `source_locator` 和 `openharmony_runtime` 的设置读写视图。OpenGrok 设置至少包括启用开关、Base URL、项目名、API 前缀、目标版本、TLS 校验、超时/重试和令牌环境变量名。路径设置只允许项目相对路径或显式绝对路径，并显示来源。

验收：保存后 Python 源码定位立即读取相同配置；旧模型配置、未知字段和密钥保持不变。

**任务 C2：设置页运行时卡片。**

在 `/settings` 增加 OpenGrok、OpenHarmony 工具链、HDC、HAP 证书和主机依赖状态卡片。页面支持刷新诊断、保存 OpenGrok 配置和跳转到本地导入说明；不显示 API Key、P12 密码或私钥内容。

验收：页面能区分模型配置和运行环境配置；错误信息能指导用户修复而不是只显示“失败”。

### 阶段 D：集成与回归

**任务 D1：接入所有动态与设备流程。**

设备资产发现使用统一 HDC；HAP 构建、签名、安装和卸载使用统一 runtime；源码定位使用设置页中的 OpenGrok 配置。日志记录工具来源、版本和健康检查摘要。

**任务 D2：测试与文档。**

补充配置 round-trip、解析优先级、URL 校验、密钥不回显、证书权限和无工具诊断测试；更新部署文档，明确可随项目交付的内容与必须由用户提供的主机依赖。

## 5. 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 只有项目内 runtime | 能解析 HDC；若 SDK 完整则能构建 HAP |
| 只配置 `VULNFOUNDER_HDC` | 设备资产发现可用，其他工具按设置或项目包查找 |
| 工具链缺少 Node/Hvigor | 前端显示缺失组件与修复建议，不生成伪成功 HAP |
| 证书目录缺失或权限过宽 | 签名前阻止并显示文件级原因 |
| OpenGrok URL 保存 | 源码定位读取设置页配置，不再依赖页面输入 |
| 配置中含密钥 | 页面和日志均不回显，文件权限保持 0600 |
| 项目目录整体迁移 | 相对路径仍有效，绝对路径只作为明确的高级覆盖 |

## 6. 风险与处理

| 风险 | 处理 |
|---|---|
| 完整 SDK 体积过大 | 提供平台化最小包/导入器，清单记录版本，避免无提示复制多 GB 文件 |
| OpenHarmony 工具跨平台不兼容 | 每个平台独立 runtime 清单，启动前检查可执行格式 |
| 私钥泄露 | `.gitignore`、0600、页面不回显、日志只记录摘要；生产证书不内置 |
| 用户配置覆盖旧字段 | 使用现有 raw map 合并与原子写入，增加 round-trip 测试 |
| OpenGrok 服务迁移 | URL、项目、版本和 TLS 均由设置页管理，认证仅引用环境变量 |

## 7. 完成标准

完成本计划后，用户在一份 VulnFounder 项目目录内即可获得工具发现、版本诊断、HDC 设备检查和 HAP 构建入口；只需在设置页填写 OpenGrok 地址等部署相关信息，不需要修改源码或在多个业务页面重复填写。任何不能随项目安全分发的内容，都必须以明确的导入、权限和缺失诊断呈现，不以硬编码路径或隐式回退掩盖。
